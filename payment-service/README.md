# Учебный сервис переводов

Два пользователя имеют по счёту в рублях. Начальные остатки — 1 000 рублей на счёте 1 и 200 рублей на счёте 2. Все суммы в базе и API выражены в копейках. Сервис доступен локально. Клиент выбирает счёт отправителя, вход пользователей в эту версию не входит.

## 1. Запустите PostgreSQL и приложение

Откройте Docker Desktop. В терминале перейдите в папку с этим файлом и выполните:

```sh
docker compose up --build -d
docker compose ps
docker compose logs --tail=30 app
```

Первый запуск скачивает образы и зависимости Maven. Дождитесь строки `Started ApplicationKt` в журнале приложения. Compose хранит БД в отдельном томе. Повторный запуск сохраняет остатки и операции.

## 2. Проверьте начальные счета

```sh
docker compose exec -T db psql -U payments -d payments -c 'SELECT id, user_id, balance FROM accounts ORDER BY id;'
```

Таблицы и начальные данные заданы в `src/main/resources/schema.sql`. Счёт принадлежит пользователю, платёж ссылается на отправляющий и получающий счета.

## 3. Переведите 150 рублей

```sh
curl -i http://127.0.0.1:18080/payments \
  -H 'Content-Type: application/json' -H 'Idempotency-Key: lesson-1' \
  -d '{"sender":1,"recipient":2,"amount":15000}'
```

В ответе появятся UUID платежа и статус `SUCCEEDED`. Повторите запрос без изменений и сравните UUID. Затем повторите SQL-команду шага 2. На исходной паре после первого перевода остатки равны 85000 и 35000 копеек, повтор их сохраняет. Чтобы прочитать результат, подставьте UUID из ответа:

```sh
curl "http://127.0.0.1:18080/payments/ВАШ-UUID"
```

## 4. Проверьте отказ по остатку

```sh
curl -i http://127.0.0.1:18080/payments \
  -H 'Content-Type: application/json' -H 'Idempotency-Key: lesson-2' \
  -d '{"sender":1,"recipient":2,"amount":100000}'
```

Ожидается HTTP 200 и статус платежа `DECLINED`: сервис обработал запрос и сохранил отказ. Остатки остаются прежними. Если повторить запрос с ключом `lesson-1`, изменив сумму, ответом будет HTTP 409.

## 5. Сохраните протокол для главы 3

```sh
python3 scripts/demo.py
```

Сценарий создаёт отдельную пару счетов, проводит три проверки и читает успешный платёж по UUID. В папке `results` появится протокол запросов, ответов и фактических остатков. Для каждого запуска создаётся новая пара счетов.

## 6. Остановите стенд после работы

```sh
docker compose down
```

Для следующего запуска выполните `docker compose up -d`.

## Как устроена операция

В `PaymentController.kt` описаны два HTTP-метода. В `PaymentService.kt` метод `transfer` выполняется в транзакции. Сервис блокирует счета в порядке их идентификаторов, ищет предыдущий результат по отправителю и ключу, затем проверяет остаток. При успешном переводе обновляет оба баланса и сохраняет платёж до фиксации транзакции. При недостатке средств записывает отказ. Ограничение уникальности в БД закрепляет правило «один отправитель и один ключ — один платёж».

## Мониторинг двух экземпляров

После запуска стенда откройте http://127.0.0.1:19090/targets. Prometheus опрашивает
`app:8081` и `app2:8081` каждые 5 секунд через внутреннюю сеть Compose.
В интерфейсе запросов выполните `up{job="payments"}`. Значение 1 означает успешный
сбор метрик с экземпляра, 0 — ошибку последнего опроса.

Для демонстрации выполните `docker compose stop app`, дождитесь состояния DOWN
для app и обновите страницу Targets. Оставшийся экземпляр должен быть UP.
Для проверки самого API прочитайте ранее сохранённый платёж через Nginx на
порту 18082. Выполните `docker compose start app` и дождитесь, пока оба экземпляра
снова отобразятся как UP. Историю значений можно посмотреть на графике запроса.
